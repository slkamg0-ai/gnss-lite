# 간이측량기 (GNSS-Lite)

폴대 + UM982 + 스마트폰으로 쓰는 **현장용 간이측량/시공 앱** (PWA, 설치 불필요·오프라인 동작).
목표 시나리오: 맨홀1~맨홀2 관로를 5m 측점으로 나눠 → 측점 찾기(스테이크아웃) → GL 측량 → 터파기(성토) 깊이 마킹 → 도면·DXF·표 출력.

## 실행
```bash
cd gnss-lite
python -m http.server 8765      # PC에서 확인: http://localhost:8765
npm test                        # 계산 로직 34개 테스트 (proj4 대조 포함)
```
휴대폰에서 쓰려면 이 폴더를 **HTTPS**로 호스팅해야 합니다(위치·서비스워커·시리얼 API 조건). GitHub Pages / Netlify / Cloudflare Pages 무료 호스팅 가능.
Chrome에서 열고 ⋮ ▸ **홈 화면에 추가** → 이후 오프라인에서도 실행됩니다.

## 화면
| 탭 | 기능 |
|---|---|
| 🎯 시공 | 구간 선택 → 측점 칩(5m) → **조준판**(위=관 진행방향, 중심=목표) + 전/후·좌/우·거리(cm) → `GL 확정`(FIXED 연속 N초 평균) → 터파기/성토 + 마킹 문구 |
| 📍 측량 | 점 측량(평균), 점 2개 탭 → 수평거리·ΔZ·경사거리·경사%·방위, 좌표 붙여넣기 가져오기 |
| 🗺️ 도면 | 평면도(팬/핀치/탭), 현위치, 측점 결과, **DXF / 점 CSV / 마킹표 CSV / 출력(PDF)** |
| 📏 구간 | 맨홀 좌표·관저고·측점 간격·굴착저면 오프셋(관저고 − x m) |
| ⚙️ 설정 | 위치 소스, 좌표계(5186/5185/5187/5188/5179/5174/5178), 안테나 높이, 평균 시간, 허용오차, **현장 보정**, 백업 |

## 위치 소스 (설정)
1. **폰 GPS (권장)** — SW Maps / Lefebure NTRIP Client가 UM982+NTRIP(vrs.ngii.go.kr:2101)을 처리하고 *모의 위치(Mock location)* 로 내보내면, 이 앱은 그 위치를 사용합니다. Fix 종류는 보고된 정확도로 추정(≤5cm FIXED, ≤0.5m FLOAT).
2. **USB 시리얼** — Web Serial로 UM982 NMEA(GGA + GST) 직결. 수신기에 RTCM이 공급되는 구성에서만 RTK.
3. **데모** — 가상 위치(연습·검증용). 데모 데이터에는 SIM 표시.

## 검증 결과 (2026-09-30)
- 좌표변환: proj4 대비 5개 좌표계 × 5개 지점 **1mm 이내**.
- 50m/Δ0.3m 관로, 5m 간격 11측점 전체 자동 시뮬레이션: 터파기 산출 오차 **±5mm 이내**.
- NMEA(체크섬·조각 스트림·GGA/GST) → 좌표 복원 mm 일치, 변조 문장 무시.
- FLOAT/SINGLE에서 측량 잠김, 수신 끊김/고도 없음 경고.
- 현장 보정(1점·2점) 잔차 0, DXF는 ezdxf 감사 오류 0(한글은 `\U+` 이스케이프), CSV/인쇄표 생성.
- 서비스워커 오프라인 캐시 9개 파일 확인.

## ⚠️ 아직 검증되지 않은 것 (실장비 필요)
- **실제 폰·UM982·BT-T009로 시험하지 않았습니다.** 위 결과는 시뮬레이터·합성 NMEA 기준입니다.
- Web Serial / Web Bluetooth(Android Chrome) 실기기 동작, UM982 출력 명령(`GPGGA/GPGST <포트> 0.5`)은 제조사 매뉴얼로 확인 필요.
- 브라우저는 NTRIP(TCP)에 직접 접속할 수 없어, **ESP32 브리지(아래)** 가 NTRIP을 대신하거나 SW Maps 모의위치를 씁니다.
- **높이 기준**: GGA 고도는 수신기 지오이드(MSL) 기준 → 국가 지오이드와 차이가 날 수 있으므로 *기지점 보정(높이)* 을 권장. RTK 수직정밀도는 수평의 약 1.5~2배.
- **폴 기울기**: 1.8m 폴이 3° 기울면 수평 약 9.4cm 오차(수직 약 2.5mm). IMU(BNO085) 기울기 보정을 구현했지만(아래) 실기기 검증 전이므로 버블 수평은 계속 맞추세요.
- NMEA 위경도 소수 자릿수가 적은 수신기는 좌표 분해능이 떨어집니다(분 단위 소수 7자리 ≈ 0.2mm, 5자리 ≈ 2cm).

# 하드웨어 조합 (구매 부품 기준) + 기울기 보정

```
 [BT-T009 안테나]─SMA─▶[UM982 보드] ◀─UART(3.3V)─▶[ESP32 DevKit] ◀─I2C─[BNO085 (Adafruit 4754)]
                                                      │  ▲
                              Wi-Fi(핫스팟) ─ NTRIP ──┘  └─ BLE ──▶ 폰 앱(PWA, Web Bluetooth)
```
ESP32 한 개가 ① UM982 NMEA 읽기 ② 폰 핫스팟으로 NTRIP 접속해 RTCM을 UM982에 공급 ③ BNO085 자세 읽기 ④ BLE로 앱에 전송을 맡습니다.
→ SW Maps 없이 앱 하나로 RTK + 기울기 보정. (앱 설정 ▸ 위치 소스 ▸ **ESP32 BLE**)

## 배선
| ESP32 DevKit | 연결 |
|---|---|
| GPIO16 (RX2) | UM982 **TX** |
| GPIO17 (TX2) | UM982 **RX** |
| GPIO21 / GPIO22 | BNO085 **SDA / SCL** (3V3, GND) |
| 5V(VIN) / GND | 전원 (아래 참고) |

## 구매 목록 검토 — 부족/주의
- ❗ **5V 승압(boost) 모듈이 없습니다.** TP4056은 *충전*만 하고 출력은 3.7~4.2V입니다. UM982 보드(USB 5V)와 ESP32 VIN(5V)에는 부족하니 **5V 부스트 컨버터(MT3608 등, 1A 이상)** 또는 5V 보조배터리가 필요합니다.
- ⚠ 3.7V 3000mAh 리튬폴리머의 **JST 1.25 커넥터 극성**은 제품마다 다릅니다. 연결 전 멀티미터로 +/− 확인. TP4056은 *보호회로(DW01) 포함형*인지 확인.
- ⚠ **UM982 보드의 UART 헤더**(핀 배치·로직 레벨 3.3V·포트명 COM1/2/3)는 도착 후 매뉴얼로 확인. 펌웨어의 `UM_PORT`를 맞추세요. UM982 USB 포트는 PC에서 UPrecise로 설정용으로 사용.
- ⚠ BNO085(4754)는 STEMMA QT 커넥터 → 헤더 핀 케이블(또는 납땜) 필요. I2C 주소 0x4A. ESP32의 I2C clock-stretching 이슈가 알려져 있어 안정성은 실측 확인.
- BNO085 **자력계는 자성체/전류선 근처에서 틀어집니다.** IMU를 UM982 보드·배터리 전선·모터/스피커에서 멀리 두세요. (알루미늄 원판·카본 폴은 영향 작음)
- 폴 상단에 IMU를 **폴 축과 대략 평행/수직 어느 쪽이든** 고정해도 됩니다(수평 캘리브레이션이 폴 축을 학습). 단, 폴에 **단단히** 고정(흔들림·유격 금지).
- 여분: ESP32 2개, BNO085 2개, 확장보드 2개 — 시제품 1대 + 예비 가능.

## 펌웨어
`firmware/gnsslite_bridge/gnsslite_bridge.ino` (PlatformIO 빌드 확인: ESP32 DevKit, Flash 80%).
```bash
pip install platformio
cd firmware && python -m platformio run                 # 빌드
python -m platformio run -t upload                      # ESP32를 USB로 연결 후 업로드
```
장치 이름 `GNSSLite`. 앱 ▸ 설정 ▸ ESP32 BLE ▸ *브리지 설정*에서 핫스팟 SSID/PW, NTRIP(vrs.ngii.go.kr:2101, 마운트/ID/PW)를 전송하면 ESP32 저장소(NVS)에 저장됩니다.

## 기울기 보정 사용법
1. 설정 ▸ *기울기 보정 사용* 체크, 자북 편차 입력(한국 약 −8.5°, 동쪽 +).
2. **① 수평 캘리브레이션**: 폴을 버블 수평으로 세워 3초 → 폴 축 학습(IMU 장착 방향 무관).
3. **② 방위 캘리브레이션**: 폴 끝을 고정하고 관 진행방향으로 5~10° 기울여 누르기 → 자력 오프셋 보정.
4. 이후 지반 좌표 = 안테나 위치 − h·(sinθ 방향, cosθ 높이). 기울기가 한계를 넘으면 측량 잠김, **자력 불량(mag<2)** 이면 수평 보정을 끄고 허용각을 `asin(허용오차/h)`(≈1°)로 제한.
5. 첫 실측 때: 폴을 **북쪽으로 기울여** 앱의 기울기 방위가 북(자북 편차 반영 후)으로 나오는지 확인. 반대/틀어지면 *IMU 세계 프레임*을 ENU↔NED로 바꾸고 다시 캘리브레이션.

### 기울기 보정 검증 (시뮬레이터·합성 NMEA, 2026-09-30)
- 5° 기울임: 보정 OFF 158mm 오차(이론 157mm) → 보정 ON 잔차 = GNSS 노이즈(~10mm). 무잡음 합성 데이터에서는 0.5mm 이하.
- 방위 캘리브레이션: 자북 편차를 0으로 잘못 넣어도 오프셋 −8.5° 복원, 다른 방위에서 9mm.
- 자력 불량/폴 축 미설정/IMU 끊김 → 측량 잠김. ESP32 BLE 경로 데이터 흐름($PIMU·GGA·$PSTAT, NED 프레임) 검증.
- **실제 BNO085 좌표계·자력 성능, BLE 처리량, UM982 명령은 실기기 미검증.**

# 권장 1단계: 폰 고정형 최소 구성 (케이블 1개)

```
[BT-T009 + 100mm 원판] ─SMA─ [UM982 USB 보드] ─USB-C─ [스마트폰 (폴 홀더에 고정)]
                                                        ├ SW Maps: USB 수신 + NTRIP → 모의 위치
                                                        ├ 간이측량기 앱: 스테이크아웃/도면/출력
                                                        └ 폰 내장 센서: 기울기 보정 (설정 ▸ IMU 소스 ▸ 폰 내장 센서)
```
ESP32·BNO085·배터리·충전·승압 모듈이 모두 필요 없습니다(보류). 전원은 폰이 USB로 공급.

## 사용 절차
1. 앱 설정 ▸ 위치 소스 = **폰 GPS**, SW Maps에서 UM982(USB) + NTRIP 연결 + 모의 위치 켜기.
2. 설정 ▸ 폴 기울기 보정 ▸ 사용 체크, IMU 소스 = **폰 내장 센서**, 최대 허용 기울기 기본 **3°**.
3. 폰을 폴에 홀더로 **견고히** 고정한 뒤 수평 캘리브레이션 → 방위 캘리브레이션 (홀더를 다시 끼우면 처음부터 다시).
4. 안테나 높이(h) 입력 — 아래 폴 메모 참고.

## 폴 메모 (탄소 74–180cm 3섹션 텔레스코픽, 5/8×11, 약 1.0kg — 판매 페이지 기준)
- **안테나 높이 h = 폴 끝(팁)에서 안테나 위상중심까지, 현재 펼친 길이 기준**입니다. 텔레스코픽이라 펼침 길이가 바뀌면 h도 바뀝니다. 폴 길이(1.80m) + 어댑터·원판·안테나 높이(수 cm)를 줄자로 재서 입력하세요(설계상 1.80은 참고값일 뿐).
- 가능하면 **완전히 펼쳐 고정한 상태(180cm)** 로 쓰세요. 섹션 사이 유격과 휨은 IMU가 보정하지 못합니다. 펼침 길이를 바꾸면 h와 수평 캘리브레이션을 다시 확인.
- 폰 홀더는 **안테나가 붙은 최상단 섹션**에 클램프(가슴 높이)로 고정하세요. 폰과 안테나가 같은 섹션이면 섹션 유격의 영향이 최소입니다. 클램프 내경이 섹션 외경과 맞는지 판매자에게 확인.
- ⚠ **자석식 폰 거치대(MagSafe 등) 금지**: 자력계가 틀어져 방위가 어긋납니다. 기계식 클램프를 쓰세요. 폰 케이스 자석도 제거.
- 카본/알루미늄은 자성체가 아니라 자력계 영향은 작습니다(단, 폰 본체 전류·USB 케이블 근처의 자기장은 캘리브레이션으로 대부분 흡수).

## 폰 센서 기울기 보정 검증 (합성 이벤트, 2026-09-30)
- W3C DeviceOrientation(absolute) → ENU 쿼터니언 변환 4방향 검증, 폰을 폴에 임의 각도로 고정해도 수평 캘리브레이션 후 3°/2°/1° 지면점 복원 오차 0.5mm 이하(무잡음).
- 소스 게이트: 폰/외부/데모 IMU가 서로 섞이지 않음.
- **미검증**: 실제 폰의 자력계 방위 정확도(추정 2~5°), SW Maps의 UM982 USB 직결 호환, Android Chrome의 deviceorientationabsolute 동작.

| **내보내기** | DXF(선형·측점·결과·찾기결과·면적 레이어), 점/선형표/찾기결과/면적 CSV, 인쇄(선형표+찾기결과+면적표+평면도) |

검증: 실제 도면(송산 오수계획평면도 10.9MB, AC1032, CP949)을 0.25초에 읽고, 텍스트 2,638·선 126·원 782·삽입 14·폴리라인 전수가 ezdxf와 좌표까지 일치. 자동 테스트 74개.

한계: DWG·바이너리 DXF, HATCH·DIMENSION·ELLIPSE·SPLINE, 블록 내부 전개는 미지원. 도면 좌표계가 앱 좌표계(설정)와 같아야 하며(경고 표시), 선형은 직선 꼭짓점 근사(원곡선·종단곡선 계산 없음). 면적은 평면 면적. DXF 배경은 브라우저 저장소(IndexedDB)에 보관되며 JSON 백업에는 포함되지 않음. 점 찾기 조준판은 북이 위(방향 센서 없음).

# 수신 기록 · 데이터 수집 (도심지 다중경로/신뢰도 모델의 첫 단계)

설정 탭 ▸ **수신 기록 · 데이터 수집**.

| 항목 | 내용 |
|---|---|
| **측정 특징 로그 (상시)** | 점·찾기·면적·보정·정답점 측정을 확정할 때마다 1건 자동 저장: 현장 유형·메모, 대기시간·재시도 횟수, Fix 비율, 위성 수/HDOP/σ, 기울기, 위성 특징(가시·사용 위성 수, 평균 C/N0, 최저 고도각, 저고도·약신호 위성 수, PDOP) → CSV 내보내기 |
| **연속 세션 로그 (선택)** | 켜 두는 동안 원문 NMEA / 에포크(좌표·Fix·σ·위성수·기울기) / 위성 스카이(1Hz: 구성·PRN·고도각·방위·C/N0·사용여부) 저장 → NMEA·에포크 CSV·위성 CSV·JSON 내보내기 |
| **정답점 측정** | 좌표를 아는 점(기지점·맨홀)에서 측정하면 오차(보정 후/전)가 **정답 라벨**로 기록됨 |
| **스카이 플롯** | 가시 위성의 위치와 C/N0 색(녹색 ≥40 / 황색 ≥32 / 적색 <32), 사용 위성은 큰 점 |

- 위성 정보(GSV/GSA)는 **USB 시리얼·BLE(ESP32) 소스와 데모**에서만 들어옵니다. SW Maps 모의위치(폰 GPS) 경로는 좌표만 전달하므로 위성 특징은 비어 있습니다.
- ESP32 펌웨어는 GSV/GSA도 BLE로 전달하도록 수정(빌드 확인). UM982 출력 명령(`GPGSV/GPGSA <포트> 1`)은 매뉴얼로 확인 필요.
- 데이터는 이 기기 브라우저(IndexedDB)에 저장되며, **내보내기 후 PC에서 분석**합니다.

## 데이터 수집 권장 절차
1. **정답점 확보**: 좌표를 아는 점 5~10개(기지점·맨홀, 트라이포드 측량점). 실측 거리(예: 75.00 / 51.50 / 2.944 m)도 정답으로 활용 가능.
2. **현장 유형을 바꿔가며**: 개활지 · 가로수 · 건물 한쪽 · 좁은 골목 · 고층 사이. 같은 점을 시간대(오전/오후)와 날씨를 바꿔 반복.
3. 점마다 **정답 측정을 3회 이상** + 연속 기록은 현장 시험 시 켜기. 현장 유형·메모를 항상 입력.
4. 모델 학습·검증은 **현장 단위로 분리**(같은 현장을 학습과 검증에 함께 쓰지 않음).
5. 지표: Fix율, 올바른 Fix율(수평 오차 ≤ 3 cm), 오Fix율, Fix까지 시간.

검증(데모 하늘·합성 데이터): GSV/GSA 파싱 테스트 2건 추가(총 76), 가상 위성 29개가 파서 경로로 유입, 30초 기록에서 에포크 150·위성 30행·NMEA 390줄(전부 파싱 성공) 저장/내보내기, 측정 특징·정답 라벨·CSV(51열) 확인, 세션 삭제 시 저장소 조각 제거 확인.
**실제 수신기(UM982)의 GSV/GSA 출력, 다중 신호(L1/L2/L5) 표기, 기록 용량(1시간 5Hz 기준)은 실기기 미검증.**

## 음성·자연어 명령 (AI)

- 🎤 버튼 → 음성(Web Speech, 한국어) 또는 글자 입력. 안내는 TTS로 읽어줌(전진/후진/좌우 거리, 도착).
- **1단계 로컬 규칙(`nlu.js`)**: "P1 찾아줘", "다음 측점", "누가거리 35에서", "오프셋 우측 0.5", "확정" 등. 인터넷·키 없이 동작, 비용 0.
- **2단계 LLM 보조(선택)**: 로컬이 못 알아들은 말만 Anthropic Messages API(공식 SDK, `vendor/anthropic.bundle.js` 로컬 번들, `npm run build:sdk`)로 보냄. 모델은 **도구 호출 1개**만 반환(strict 스키마 24종), 앱이 이름·타입·범위를 다시 검증. 모호하면 `ask_user`로 되물음. 설정 탭 "AI 해석"에서 키 입력(이 기기 브라우저에만 저장, 백업 JSON에서는 제외). 판매용은 키를 앱에 넣지 말고 중계 서버를 둘 것.
- **안전 규칙**: 측정·삭제·오프셋 등 `confirm` 위험도 명령은 "예/아니오"로 명시 확인 후 실행, 실행 후 ↶ 실행취소 가능. LLM에는 발화 + 점/선형 **이름** + 현재 모드만 전송(좌표·측정값 미전송).
- **기록**: 모든 명령이 cmdlog(IndexedDB)에 발화·해석·성공 여부·출처(local/llm)·토큰으로 저장 → 음성 인식/해석 정확도 증빙 자료.
- 테스트: `npm test` = core 65 + dxf 11 + nlu 26. 브라우저에서 가짜 API 서버(`window.__llmFetch`)로 요청 형태(URL `?beta=true`, 폴백 베타 헤더, effort low, tool_choice auto), 400→일반 재시도, ask_user, 환각 이름 거부, refusal, 네트워크 실패, confirm→실행→undo, 로컬 해석 시 API 미호출을 확인함.
- **미검증(실제 환경 필요)**: 실제 API가 `fallbacks:'default'` 베타를 받는지(안 받으면 자동으로 일반 호출로 재시도), 안드로이드 Chrome 실제 마이크/TTS, 현장 소음에서의 인식률.

## 안내 음성 업그레이드 (ElevenLabs, 선택)

- 설정 ▸ "안내 음성": 엔진을 ElevenLabs로 바꾸고 API 키 입력 → 목소리 불러오기 → 시험 재생. 기본은 폰 내장 음성.
- 문구를 쉼표 단위로 나눠 생성하고 IndexedDB(`tts:<voice>:<model>:<문구>`)에 캐시 → 같은 문구는 오프라인·무료·즉시. 거리 안내는 5 cm / 0.1 m 단위로 묶어 적중률을 높임. 실패·미캐시 오프라인이면 기본 음성으로 자동 대체.
- 무료 플랜은 월 크레딧이 작음(Flash 0.5/글자). "자주 쓰는 안내 미리 만들기"로 고정 문구를 한 번에 저장. 앱은 이 폰에서 생성한 글자 수만 센다(실제 잔량은 ElevenLabs 사이트).
- 검증됨(가짜 서버): 요청 형태(URL, `xi-api-key`, model_id), 문구 분할·캐시 적중(새 부분만 호출), 오프라인 캐시 재생/미캐시 오류, 실패 시 기본 음성 대체, 백업에 키 미포함.
- 미검증: 실제 ElevenLabs 응답(키 필요), 무료 플랜에서 라이브러리 목소리의 API 사용 가능 여부(막히면 기본 제공 목소리 선택), 폰에서 자동재생 허용 여부, 상업 이용 조건.

## 안테나 장착 어댑터 (3D 프린트, `hardware/`)

- BT-T009 는 5/8" 나사가 없고 M3 구멍 4개(중심 간격 28.284 mm = Ø40 원 위 정사각 배치, DXF 구멍 원 4개의 중심으로 확인, 귀 바깥 끝은 구멍 중심에서 4.857)로 체결한다. 어댑터가 안테나를 잡고 100 mm 알루미늄 원판의 5/8"-11 암나사에 돌려 끼운다.
- `python hardware/antenna_mount.py` → `antenna_mount.stl`(출력용, 체결면이 베드·볼트부가 위) + `antenna_mount.dxf`(평면·단면 도면). 치수는 스크립트 위쪽 `P` 만 고치면 다시 만들어진다.
- 구조(외곽 원형 Ø50, `P['shape']='square'` 로 40x40 둥근 사각형도 가능): 총높이 30 mm(체결판 6 + 속 빈 몸통 + 바닥 5), 5/8"-11 수나사 7 mm 돌출, Ø24 속 공간(안테나 목·케이블), 옆 창 11 mm(SMA 커넥터 통과), M3 셀프탭 밑구멍 Ø2.8 x 깊이 8.
- 검증: STL 껍질 6개 모두 닫힘(비정상 모서리 0), 부피가 해석값과 일치, DXF 감사 오류 0.
- **미검증(실물 필요)**: 안테나 귀 구멍 실측 간격, 목(Ø20)의 돌출 길이, 원판 중앙 나사가 관통인지, 나사 공차(0.35)·3바퀴 체결 강도. 처음엔 나사부만 짧게 시험 출력해 원판에 끼워 보고 전체를 출력할 것.
- 창 방향: 기본은 정면 1개(`antenna_mount.stl`, 설계 좌표 -y = 평면도 아래쪽). 나사를 조이는 각도에 따라 창이 정면을 벗어날 수 있어 4면 창 버전(`antenna_mount_4window.stl`)도 함께 만든다. 방향은 `P['windows']`(도)로 지정.

## 핸즈프리 음성 (호출어) — 실험 기능
- 🎤 시트의 **핸즈프리 (호출어)** 를 켜면 앱이 계속 듣다가 호출어("측량기") 뒤의 말만 명령으로 처리한다. 호출어 없이 들린 말은 버린다(확인 질문에 대한 "예/아니오"만 예외). 호출어만 말하면 다음 한 마디(6초)를 명령으로 받는다. 호출어 소리는 짧은 알림음.
- 호출어 오인식 대비: 쉼표로 변형 여러 개 지정(기본 4개), 4글자 이상이면 한 글자 오인식 허용.
- 자기 안내 음성(TTS)을 다시 듣지 않도록 안내하는 동안은 인식 결과를 무시한다. 측정·오프셋 같은 위험 명령은 여전히 "예/아니오" 확인 후 실행된다.
- 앱을 껐다 켜면 🎤를 한 번 눌러 다시 켠다(브라우저 정책상 사용자 터치 필요).
- 한계(안드로이드 Chrome Web Speech API 상시 인식): 인식이 수시로 끊겨 다시 시작해야 하고 시작음이 날 수 있음, 화면이 켜진 앱 전면에서만 동작, 오디오가 클라우드로 전송됨, 배터리 소모. **실기기 미검증**이며 거슬리면 기기 안 호출어 감지(2단계)로 옮긴다.
- 검증(가짜 인식기): 호출어 찾기(공백·변형·오인식), 잡담 무시, 호출어+명령, 호출어 단독 후 명령, 6초 만료, 안내 음성 중 무시, 확인 질문 예/아니오, 끊김 시 자동 재시작, 권한 거부 시 자동 끔.

## 수신 진단 (현장 문제 보고용)
- 설정 ▸ **수신 진단**: 최근 60초의 위치 갱신 횟수(Hz, 최대 간격), FIXED 비율, 수평 정확도 최소/최대/마지막, 고도 포함 여부, 현재 경고, 마지막 측정 성공/실패 이유. **진단 복사 / 공유** 버튼으로 내보낸다(좌표 미포함).
